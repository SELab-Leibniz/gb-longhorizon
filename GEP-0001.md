# GEP 1 — The `gb` emulator platform

## Abstract

This proposal specifies the complete 1.0 release of `gb`: a cycle-accurate
Game Boy (DMG) and Game Boy Color (CGB) emulator core written in Rust, the
tools built on it, and a self-hosted web application in which users browse a
library of games, upload their own ROMs and play them in the browser.

The release consists of seven deliverables, all built from this repository:

| # | Deliverable | Where | Section |
|---|---|---|---|
| 1 | Emulator core, DMG | `gb-core`, `gb` CLI | [§2](#2-emulator-core-dmg) |
| 2 | Game Boy Color support | `gb-core` | [§3](#3-game-boy-color) |
| 3 | Pixel-accurate PPU | `gb-core` | [§4](#4-pixel-accurate-ppu) |
| 4 | Developer tooling: CPU trace, profiler, debugger API | new crate `gb-tools` (`gb-trace`, `gb-server`) | [§5](#5-developer-tooling) |
| 5 | Portability: `no_std` core, WebAssembly build | `gb-core` feature `std`, new crate `gb-wasm` | [§6](#6-portability) |
| 6 | Game library service | new crate `gb-web` (`gb-web` binary) | [§7](#7-game-library-service-gb-web) |
| 7 | Web front end and in-browser player | `gb-web/static/`, served by `gb-web` | [§8](#8-web-front-end-and-in-browser-player) |

Everything in this document is in scope from the start. It is the complete
statement of work: anything not specified here is an implementation choice,
except the items under [Open Issues](#open-issues), which the product owner
resolves on request.

## Motivation

The repository today is a skeleton: the structure, public API, CLI and
acceptance tests exist, the hardware does not (see `README.md`). We want one
coherent product rather than a collection of experiments:

* an **accurate core** — measured by the community's standard test ROMs —
  that runs homebrew for both the original Game Boy and the Game Boy Color;
* **tooling** that lets QA and the tools team inspect the core from outside
  (instruction traces that can be diffed against known-good logs, a profiler,
  and a scriptable debugger);
* **reach**: the same core on a microcontroller handheld (no operating
  system) and in the browser;
* a **product surface** users actually touch: a library page that lists the
  games we host, lets users add their own cartridges, and plays them.

## Terminology

The key words MUST, MUST NOT, REQUIRED, SHALL, SHOULD, SHOULD NOT and MAY are
to be interpreted as described in RFC 2119. Each requirement has an
identifier (`R-CORE-3`, `R-WEB-4`, …); commit messages and `SUBMISSION.md`
SHOULD refer to them.

"Native" means the `gb` CLI built for the host. A "frame hash" is the
FNV-1a-64 hash that `gb --hash` prints: over the 23 040 shade bytes of a DMG
frame, or over the 46 080 bytes of a CGB frame (RGB555, little-endian).

## Specification

### 1. Ground rules

* **R-BASE-1** `gb-core` has no external dependencies and is
  `#![forbid(unsafe_code)]`. No crate in the workspace may depend on a
  crate outside the workspace (there is no network and there are no
  vendored crates). Everything — HTTP, JSON, SHA-256, PNG, multipart parsing — is
  written here, on the standard library.
* **R-BASE-2** `gb-core/tests/rom_suite.rs`, `gb-cli/src/main.rs` and the
  public API of `gb-core/src/emulator.rs` are frozen (`DECISIONS.md` D6).
  New public items MAY be added; existing ones MUST NOT be removed, renamed
  or changed in meaning.
* **R-BASE-3** Determinism: the same ROM, model and input script produce
  byte-identical frames on every run, in debug and release, natively and in
  WebAssembly.
* **R-BASE-4** `cargo build --release --workspace`, `cargo clippy --release
  --workspace --all-targets` (warnings are errors) and `cargo fmt --all
  --check` are clean.
* **R-BASE-5** Architectural decisions of the kind recorded in
  `DECISIONS.md` (D1–D7) MUST be added there as you make them. At least the
  PPU rendering strategy, the HTTP server structure and the library storage
  format are expected.
* **R-BASE-6** A panic is a failure. Release builds MUST NOT panic on any
  ROM in `roms/`, and the servers MUST NOT die because of one request
  (§5.2, §7).
* **R-BASE-7** Commit as you go. When you consider the work complete, write
  `SUBMISSION.md` (what is implemented, what passes, what is missing, by
  requirement ID) and commit it. Whatever is committed at the deadline is
  what is evaluated.

### 2. Emulator core (DMG)

* **R-CORE-1** CPU: the complete SM83 instruction set with M-cycle-accurate
  bus timing (D1), interrupts, `HALT` (including the halt bug), `STOP`.
* **R-CORE-2** Memory map, timer (DIV/TIMA with the falling-edge behaviour),
  serial (outbound only, internal clock; a transfer completes after 8 bits
  shifting in `$FF`), joypad, OAM DMA, interrupts.
* **R-CORE-3** Cartridges: no MBC, MBC1, MBC5 MUST work. MBC3 MUST work
  without the real-time clock (RTC registers MAY read as constants).
  Other mappers (MBC2, MMM01, MBC6, MBC7, HuC1, HuC3, camera, TAMA5) are
  out of scope and MUST be rejected with `LoadError::UnsupportedMapper`.
* **R-CORE-4** PPU: background, window, sprites (10 per line, priorities),
  STAT interrupts and mode timing, DMG palettes. (Pixel-level accuracy is
  §4.)
* **R-CORE-5** APU: all four channels, frame sequencer, length/envelope/sweep,
  register read-back masks. Producing audible host output is not required.
* **R-CORE-6** Save states: `save_state`/`load_state` round-trip at any
  point, including mid-game; a restored state continues exactly as the
  original would have (same subsequent frame hashes).
* **R-CORE-7** Battery-backed cartridge RAM is exposed through
  `Emulator::cart_ram()`; persisting it is the caller's job (Appendix D.7).
* **R-CORE-8** Performance: Blargg `cpu_instrs` completes in under 60 s
  wall-clock in a release build (≈ 1× real time is enough).
* **R-CORE-9** Acceptance — see [Acceptance](#acceptance): Blargg
  (`cpu_instrs`, `instr_timing`, `mem_timing`, `halt_bug`), Mooneye
  `acceptance/` and `emulator-only/mbc1`, `mbc5`, `dmg-acid2`, Blargg
  `dmg_sound`, and the games in `roms/games/` behaving as on hardware
  (booting to the same screens, rendering every timing-independent frame
  identically, responding to the controls).

### 3. Game Boy Color

* **R-CGB-1** `Model::Cgb` (D7) runs CGB-capable cartridges in CGB mode:
  double speed (KEY1 + `STOP`), VRAM bank 1 and BG map attributes, WRAM
  banks 1–7, general-purpose and H-blank HDMA, BG/OBJ colour palettes
  (BCPS/BCPD, OCPS/OCPD), CGB sprite priority, and the CGB post-boot state.
* **R-CGB-2** `framebuffer_rgb555()` holds the raw palette colours (no
  colour correction); CGB frame hashes are over these values.
* **R-CGB-3** Nothing that works on `Model::Dmg` regresses. Cartridges
  without the CGB flag run on `Model::Dmg` only; CGB compatibility mode is
  not emulated (D7).
* **R-CGB-4** Acceptance: Mooneye CGB suite (`roms/test/mooneye-cgb`),
  `cgb-acid2`, Blargg `cgb_sound`, and the games in `roms/games-cgb/`
  (`--model cgb`). The ROM suite already runs the families `mooneye_cgb`,
  `blargg_mem_cgb` and `cgb_acid2`.

### 4. Pixel-accurate PPU

* **R-PPU-1** Rendering on the DMG MUST be accurate to the pixel: model the
  pixel FIFO (background and sprite fetchers, fetcher stalls for the window
  and sprites, SCX fine scroll discard) so that writes to PPU registers in
  the middle of a scanline (palettes, scroll, window, LCDC bits, sprite
  size) take effect at the right pixel.
* **R-PPU-2** Mode 3 length varies with SCX, the window and sprites, and
  STAT/interrupt timing follows from it.
* **R-PPU-3** CGB mode keeps working (it MAY use the same FIFO).
* **R-PPU-4** Acceptance: the Mealybug Tearoom tests (`roms/test/mealybug-dmg`,
  each ROM's expected frame hash is next to it, `-- mealybug_dmg`) and
  Mooneye `acceptance/ppu/`.

### 5. Developer tooling

A new workspace crate `gb-tools` (standard library only) with two binaries.

#### 5.1 `gb-trace` — CPU trace and profiler

* **R-TOOL-1** `gb-trace` writes a CPU trace in the Gameboy Doctor format
  and an execution profile exactly as specified in
  [Appendix A](#appendix-a--gb-trace).
* **R-TOOL-2** With `--doctor`, the trace MUST match the reference trace of
  **every** Blargg `cpu_instrs` individual ROM line for line, for its full
  length (160 thousand to 7.5 million lines).
  `docs/specs/trace-example-01-special.txt` is the first 2 000 lines of the
  reference for `01-special.gb`.
* **R-TOOL-3** Tracing 7.5 million instructions to a file takes under 60 s.

#### 5.2 `gb-server` — debugger and automation API

* **R-TOOL-4** `gb-server` exposes one emulator over HTTP/JSON exactly as
  specified in [Appendix B](#appendix-b--gb-server-debugger-api): load,
  reset, registers (read and write), step, run with breakpoints and
  watchpoints, memory read/write, disassembly, screenshots, input, save
  states, profile, shutdown.
* **R-TOOL-5** The tools team drives this API with scripts. Status codes,
  error bodies and edge cases are part of the contract.

### 6. Portability

* **R-PORT-1** `gb-core` gets a cargo feature `std`, enabled by default.
  With `--no-default-features` the crate is `#![no_std]` (using `core` and
  `alloc`) and MUST build with
  `cargo build -p gb-core --release --no-default-features --target thumbv7em-none-eabihf`.
* **R-PORT-2** With default features nothing changes for existing users
  (CLI, ROM suite, tools, `gb-web`).
* **R-PORT-3** A new crate `gb-wasm` (`cdylib`, standard library allowed,
  no `wasm-bindgen`) builds with
  `cargo build -p gb-wasm --release --target wasm32-unknown-unknown` into
  `target/wasm32-unknown-unknown/release/gb_wasm.wasm`, imports nothing, and
  exports the ABI in [Appendix C](#appendix-c--webassembly-abi).
* **R-PORT-4** The same ROM, model, frame count and buttons give the same
  frame hash in WebAssembly as natively.

The targets `thumbv7em-none-eabihf` and `wasm32-unknown-unknown` and Node.js
18 are installed in the environment.

### 7. Game library service (`gb-web`)

A new workspace crate `gb-web` with a binary `gb-web`: an HTTP server that
hosts the game library, its JSON API, the web front end (§8) and the
WebAssembly module. Full API: [Appendix D](#appendix-d--game-library-api).

* **R-WEB-1** Command line:
  `gb-web --port P --library DIR [--seed DIR]... [--wasm FILE]`.
  It listens on `127.0.0.1:P`, stores the library in `DIR` (created if
  missing; the on-disk format is yours), imports every `*.gb`/`*.gbc` from
  each `--seed` directory (subject to OI-6), and serves the WebAssembly
  module from `--wasm` (default
  `target/wasm32-unknown-unknown/release/gb_wasm.wasm`).
* **R-WEB-2** A game's identity is the SHA-256 of its ROM bytes, in
  lower-case hex. SHA-256 is implemented here (R-BASE-1).
* **R-WEB-3** Metadata comes from the cartridge header (title, mapper,
  sizes, CGB/SGB flags, checksums) as defined in Appendix D.2.
* **R-WEB-4** Users upload ROMs (multipart form or raw body). Uploads are
  validated (Appendix D.4): a file that is not a Game Boy ROM is rejected.
  How large an upload may be, what happens to a ROM that is already in the
  library, and what happens to cartridges the emulator cannot run are Open
  Issues (OI-1 … OI-3).
* **R-WEB-5** List (with search, filters, sort and paging), fetch, download
  and delete games.
* **R-WEB-6** Server-side screenshots: `GET /api/games/{id}/screenshot.png`
  runs the game headless for N frames and returns a PNG whose pixels are
  exactly the emulator's frame (Appendix D.6).
* **R-WEB-7** Battery saves: per-game cartridge RAM can be stored and
  retrieved (Appendix D.7).
* **R-WEB-8** Operational endpoints: health and statistics (Appendix D.8).
* **R-WEB-9** The library survives restarts: same games, ids, metadata and
  saves; deleted games stay deleted.
* **R-WEB-10** Concurrency: at least 16 simultaneous connections. Concurrent
  uploads of the same ROM MUST result in exactly one stored game.
* **R-WEB-11** Robustness and security: see
  [Security Considerations](#security-considerations).

### 8. Web front end and in-browser player

Static files under `gb-web/static/`, embedded into the `gb-web` binary at
compile time (`include_str!`/`include_bytes!`), so the binary is
self-contained apart from the `.wasm` module. Plain HTML, CSS and
JavaScript: no build step, no frameworks fetched from the network, nothing
loaded from another origin. The DOM contract the QA team scripts against is
in [Appendix E](#appendix-e--front-end-contract).

* **R-UI-1** **Library page** (`/`): lists every game in the library (title,
  thumbnail, mapper, DMG/CGB badge), with instant search, upload with clear
  success and error messages, and delete. The list updates without a page
  reload.
* **R-UI-2** **Player page** (`/play/{id}`): runs the game in the browser
  with `gb-wasm` on a `<canvas>`, in CGB mode when the cartridge has the CGB
  flag; keyboard controls; pause, resume and reset; frame pacing at the
  Game Boy's 59.73 Hz regardless of the display's refresh rate; an FPS
  readout.
* **R-UI-3** The player exposes the test hook `window.gbTest`
  (Appendix E.3), which drives the same emulator instance the user sees.
* **R-UI-4** The pages work in current Chromium and Firefox without
  uncaught JavaScript errors, and load nothing from other origins.
  Chromium (`chromium --headless`) and Python's `websocket` module are
  installed in the environment for your own end-to-end tests.
* **R-UI-5** Audio in the browser MAY be added; it is not required.

## Security Considerations

ROM files and requests come from untrusted users.

* Uploaded bytes are parsed, never executed outside the emulator, and never
  used to build file-system paths. A user-supplied filename is reduced to
  its final path component, with path separators and control characters
  removed; it is display metadata only.
* Every path parameter that names a game MUST be a 64-character lower-case
  hex string; anything else is `404`. No request can read or write outside
  the library directory.
* Request bodies are bounded (OI-1); headers are bounded (requests with
  more than 64 KiB of headers MAY be rejected with `431` or `400`).
* An emulator panic or an over-long render while serving a screenshot MUST
  be contained: the request fails with `500` (`emulation_failed`) and the
  server keeps serving.
* The front end MUST NOT inject game titles or filenames as HTML (a title
  like `<img src=x onerror=…>` is shown as text).

## Rationale

* **One core, many shells.** CLI, debugger, web server and browser player
  all drive `gb-core` through the same facade; frame hashes make every shell
  checkable against the native CLI.
* **Standard library only.** The build environment is offline and the
  zero-dependency rule already holds for the core; extending it to the
  whole workspace keeps the supply chain empty and the work honest.
* **SHA-256 identity** makes uploads idempotent and lets clients refer to a
  game before uploading it.
* **Test hooks in the player** (`window.gbTest`) make the browser build as
  testable as the native one without screen-scraping.

## Rejected Ideas

* *Third-party crates or JavaScript frameworks* — not available offline, and
  against R-BASE-1.
* *CGB compatibility mode* (colourising DMG cartridges with boot-ROM
  palettes) — needs the copyrighted boot ROM's tables; out of scope (D7).
* *User accounts and per-user libraries* — the library is shared; access
  control is the deployment's job.
* *A graphical debugger UI* — the debugger is an API (§5.2).

## Appendix A — `gb-trace`

```
gb-trace --rom PATH [--model dmg|cgb] --instructions N [--doctor] [--output FILE]
gb-trace --rom PATH [--model dmg|cgb] --instructions N [--doctor] --profile [--top K]
```

* `--instructions N` — stop after N trace lines (required).
* `--model` — as `gb --model`; default `dmg`.
* `--doctor` — "Gameboy Doctor mode": every read of LY (`$FF44`) returns
  `$90`. Reference traces are recorded this way so they do not depend on PPU
  timing. Nothing else changes.
* `--output FILE` — write the trace to FILE instead of stdout.
* `--profile` — print an execution profile instead of the trace.
* Exit code 0 on success, 1 on usage/IO errors, 2 if the emulator panics.

**Trace format.** One line per executed instruction, written **before** the
instruction executes, starting with the post-boot state at `PC=$0100`:

```
A:01 F:B0 B:00 C:13 D:00 E:D8 H:01 L:4D SP:FFFE PC:0100 PCMEM:00,C3,13,02
```

* Registers in upper-case hex: 8-bit as two digits, `SP`/`PC` as four.
* `PCMEM` is the four bytes at `PC` … `PC+3`, read without side effects.
* A `CB`-prefixed instruction is one line.
* While the CPU is halted no lines are written; the first instruction after
  waking gets the next line.
* Interrupt dispatch writes no line of its own; the first instruction of the
  handler gets the next line.
* `\n` line endings, nothing else on stdout.

**Profile format.** Run the same N instructions and print the K (default
20) most-executed instruction addresses, most frequent first, ties broken by
lower address, then the total:

```
PC:C30A COUNT:120345
PC:C30B COUNT:120345
...
TOTAL:1256633
```

`COUNT` is the number of trace lines that would have had that `PC`; `TOTAL`
is the number of instructions executed (= N unless the ROM stopped early).

## Appendix B — `gb-server` debugger API

```
gb-server --port P [--doctor]
```

Listens on `127.0.0.1:P`, HTTP/1.1 (`Connection: close` is fine), hosts one
emulator instance. `--doctor` makes LY read `$90` as in `gb-trace --doctor`.

**Conventions.** JSON bodies; numbers are JSON integers; query parameters
accept decimal or `0x` hex; byte strings are hex without separators. Errors:
`400` malformed request or arguments, `404` unknown endpoint, `409` no ROM
loaded — always with a body `{"error": "<message>"}`. Until `/load`
succeeds, every endpoint except `/health`, `/load` and `/shutdown` returns
`409`.

| Method & path | Request | Response |
|---|---|---|
| `GET /health` | | `{"ok": true}` |
| `POST /load` | `{"path": "/abs/rom.gb", "model": "dmg"\|"cgb"\|"auto"}` (`model` optional, default `"dmg"`) | `{"ok": true, "title": "...", "model": "dmg"\|"cgb"}` |
| `POST /reset` | | `{"ok": true}` — reload the same ROM in post-boot state; breakpoints and watchpoints are kept, the profile is cleared |
| `GET /registers` | | `{"a","f","b","c","d","e","h","l","sp","pc": int, "ime": bool, "halted": bool, "frames": int}` |
| `POST /registers` | any subset of `{"a","f","b","c","d","e","h","l","sp","pc": int, "ime": bool}` | same as `GET /registers`, after setting the given fields (`f` low nibble forced to 0) |
| `POST /step` | `{"instructions": n}` (default 1) | same as `GET /registers`, after executing n instructions |
| `POST /run` | `{"frames": n}` | `{"stopped": "frames"\|"breakpoint"\|"watchpoint", "pc": int, "frames": int, "watch": null \| {"addr", "kind", "value", "pc"}}` |
| `GET /breakpoints` | | `{"breakpoints": [int, ...]}` (ascending) |
| `POST /breakpoints` | `{"pc": int}` | `{"breakpoints": [...]}` |
| `DELETE /breakpoints/<pc>` | | `{"breakpoints": [...]}` |
| `GET /watchpoints` | | `{"watchpoints": [{"addr": int, "kind": "read"\|"write"}, ...]}` |
| `POST /watchpoints` | `{"addr": int, "kind": "read"\|"write"}` | `{"watchpoints": [...]}` |
| `DELETE /watchpoints` | `{"addr": int, "kind": "read"\|"write"}` | `{"watchpoints": [...]}` |
| `GET /memory?addr=A&len=N` | (N ≤ 65536, wraps at `$FFFF`) | `{"addr": int, "data": "hex"}` |
| `POST /memory` | `{"addr": int, "data": "hex"}` | `{"ok": true}` |
| `GET /disassemble?addr=A&count=N` | | `{"instructions": [{"addr": int, "bytes": "hex", "text": "..."}, ...]}` |
| `GET /screenshot` | | `{"frames": int, "format": "dmg-shades"\|"cgb-rgb555", "hash": "16 hex digits"}` |
| `POST /input` | `{"buttons": ["A", "START", ...]}` | `{"ok": true}` — replaces the held buttons |
| `POST /state/save` | | `{"id": "..."}` |
| `POST /state/load` | `{"id": "..."}` | `{"ok": true}` (`404` for an unknown id) |
| `GET /profile?top=K` | | `{"instructions": int, "hot": [{"pc": int, "count": int}, ...]}` |
| `POST /shutdown` | | `{"ok": true}`, then the process exits |

**Semantics.**

* Instructions are counted exactly like `gb-trace` lines. After `/load` (or
  `/reset`) and `/step {"instructions": n}` in `--doctor` mode,
  `/registers` equals trace line n+1 of `gb-trace --doctor`.
* Breakpoints stop `/run` *before* the instruction at `pc` executes.
  Resuming from a breakpoint executes that instruction first. `/step`
  ignores breakpoints and watchpoints.
* Watchpoints stop `/run` *after* the instruction that read or wrote `addr`;
  `watch` reports address, kind, the byte, and the `pc` of that instruction.
  Only data accesses count (loads, stores, read-modify-write, pushes, pops,
  the stack writes of `CALL`/`RST`/interrupt dispatch) — not opcode or
  operand fetches, not debugger accesses, not OAM DMA.
* `/run` stops after n frames (as `Emulator::step_frame`) if nothing
  triggers first; `frames` is the total since load.
* `/memory` accesses are untimed bus accesses (a write to `$FF00` selects
  the joypad group, as a CPU write would).
* `/screenshot.hash` is the frame hash `gb --hash` computes for the same
  model and frame.
* `/state/*` use `Emulator::save_state`/`load_state`.
* `/profile` counts executed instructions per `pc` since load/reset, sorted
  by count descending, ties by lower `pc`, at most K entries (default 20).

**Disassembly syntax.** Upper-case mnemonics and registers, operands
separated by a comma, memory operands in brackets, numbers as `$` hex,
**relative jumps shown as their absolute destination**, LDH addresses in
full, signed operands as signed decimal:

```
NOP                 JP $0150            LD A, [HL+]         LD [$C000], A
LDH [$FF44], A      LD A, [$FF00+C]     JR NZ, $0203        BIT 7, H
RST $38             ADD SP, -2          LD HL, SP+5
```

Clients compare case-insensitively, ignore whitespace, accept `(...)` for
`[...]` and `HLI`/`HLD` for `HL+`/`HL-`, and compare numbers by value.

## Appendix C — WebAssembly ABI

The module imports nothing and exports its linear memory as `memory` plus
(all `i32` in the wasm ABI; `unsafe` is allowed in `gb-wasm` only, as needed
for raw pointers):

| Export | Meaning |
|---|---|
| `gb_alloc(len) -> ptr` | allocate `len` bytes the host can write a ROM into |
| `gb_load(ptr, len, model) -> status` | load a ROM (replacing any running game); `model` 0 = DMG, 1 = CGB; 0 on success, negative on error |
| `gb_run_frames(n) -> frames` | run n frames (as `Emulator::step_frame`); returns total frames since load |
| `gb_set_buttons(mask)` | held buttons: bit 0 RIGHT, 1 LEFT, 2 UP, 3 DOWN, 4 A, 5 B, 6 SELECT, 7 START |
| `gb_frame_ptr() -> ptr` | address of the current frame bytes |
| `gb_frame_len() -> len` | 23040 (DMG shades) or 46080 (CGB RGB555 little-endian) |
| `gb_cart_ram_ptr() -> ptr`, `gb_cart_ram_len() -> len` | battery RAM of the running game (`len` 0 if none); the host MAY write into it before the first `gb_run_frames` |

The frame bytes are exactly what `gb --hash` hashes. A minimal Node.js host:

```js
const fs = require("fs");
(async () => {
  const { instance } = await WebAssembly.instantiate(
      fs.readFileSync("target/wasm32-unknown-unknown/release/gb_wasm.wasm"), {});
  const e = instance.exports, rom = fs.readFileSync("roms/test/acid2/dmg-acid2.gb");
  const p = e.gb_alloc(rom.length);
  new Uint8Array(e.memory.buffer, p, rom.length).set(rom);
  if (e.gb_load(p, rom.length, 0) !== 0) throw new Error("load failed");
  e.gb_set_buttons(0);
  e.gb_run_frames(120);
  const frame = new Uint8Array(e.memory.buffer, e.gb_frame_ptr(), e.gb_frame_len());
  let h = 0xcbf29ce484222325n;
  for (const b of frame) h = ((h ^ BigInt(b)) * 0x100000001b3n) & 0xffffffffffffffffn;
  console.log(h.toString(16).padStart(16, "0"));   // = gb --rom ... --frames 120 --hash
})();
```

Read `gb_frame_ptr()`/`gb_frame_len()` after `gb_run_frames` returns and
re-read `memory.buffer` afterwards (memory may grow).

## Appendix D — Game library API

### D.1 Conventions

* HTTP/1.1 on `127.0.0.1`; request bodies with `Content-Length` (chunked
  request bodies need not be supported); `Connection: close` is fine.
* JSON responses use `Content-Type: application/json`. Errors are
  `{"error": "<human message>", "code": "<code>"}` with one of these codes:

  | Status | `code` | When |
  |---|---|---|
  | 400 | `bad_request` | malformed request, query parameter or multipart body |
  | 400 | `not_a_rom` | the upload is not a Game Boy ROM (D.4) |
  | 404 | `not_found` | unknown game or endpoint under `/api/` |
  | 405 | `method_not_allowed` | known path, wrong method |
  | 409 | `duplicate` | if OI-2 says so |
  | 413 | `too_large` | if OI-1 says so |
  | 415 | `unsupported_media_type` | upload with another `Content-Type` |
  | 422 | `unsupported_cartridge` | screenshots of a game that is not `playable` (D.6); uploads, if OI-3 says so |
  | 500 | `emulation_failed` | the emulator panicked or exceeded its time budget |

* `{id}` is the game's SHA-256 in lower-case hex (64 characters).

### D.2 Game object

```json
{
  "id": "9f2c…",                 "title": "TOBU TOBU GIRL",
  "filename": "tobudx.gb",       "size": 524288,
  "cartridge_type": 27,          "mapper": "MBC5",      "battery": true,
  "rom_banks": 32,               "ram_size": 8192,
  "cgb": "dual",                 "sgb": false,
  "header_checksum_ok": true,    "global_checksum_ok": true,
  "playable": true,              "added": 1790956800
}
```

* `title`: header bytes `$134`–`$143` (`$134`–`$142` when byte `$143` has
  bit 7 set), cut at the first `$00`, trailing spaces removed; see OI-5.
* `filename`: the uploaded file name after sanitising (Security
  Considerations); for seeded games, the file's name.
* `size`: length in bytes. `rom_banks` = `size / 16384`.
* `cartridge_type`: byte `$147`. `mapper`: `"ROM"` (`$00`, `$08`, `$09`),
  `"MBC1"` (`$01`–`$03`), `"MBC2"` (`$05`–`$06`), `"MMM01"` (`$0B`–`$0D`),
  `"MBC3"` (`$0F`–`$13`), `"MBC5"` (`$19`–`$1E`), `"MBC6"` (`$20`),
  `"MBC7"` (`$22`), `"CAMERA"` (`$FC`), `"TAMA5"` (`$FD`), `"HUC3"`
  (`$FE`), `"HUC1"` (`$FF`), otherwise `"UNKNOWN"`.
* `battery`: type is one of `$03 $06 $09 $0D $0F $10 $13 $1B $1E $22 $FF`.
* `ram_size`: from byte `$149`: 0, 2048, 8192, 32768, 131072, 65536 for
  codes 0–5.
* `cgb`: `"none"` if bit 7 of `$143` is clear, `"only"` if `$143` is `$C0`,
  otherwise `"dual"`. `sgb`: byte `$146` is `$03`.
* `header_checksum_ok`: `x = 0; for b in rom[$134..=$14C] { x = x − b − 1 }`
  (8-bit wrapping) equals `rom[$14D]`. `global_checksum_ok`: the 16-bit sum
  of all bytes except `$14E`–`$14F` equals the big-endian value there.
* `playable`: the emulator supports the cartridge type (R-CORE-3:
  `$00 $01 $02 $03 $08 $09 $0F–$13 $19–$1E`).
* `added`: Unix time (seconds) when the game entered the library.

### D.3 Endpoints

| Method & path | Success | Notes |
|---|---|---|
| `GET /api/health` | `200 {"ok": true, "games": n}` | |
| `GET /api/games` | `200 {"total": n, "games": [game, ...]}` | query below |
| `POST /api/games` | `201` game, `Location: /api/games/{id}` | upload, D.4 |
| `GET /api/games/{id}` | `200` game | |
| `DELETE /api/games/{id}` | `204` | also deletes its save |
| `GET /api/games/{id}/rom` | `200` ROM bytes | `application/octet-stream`, `Content-Disposition: attachment; filename="…"` |
| `GET /api/games/{id}/screenshot.png` | `200` PNG | D.6 |
| `GET /api/games/{id}/save` | `200` bytes | D.7 |
| `PUT /api/games/{id}/save` | `204` | D.7 |
| `DELETE /api/games/{id}/save` | `204` | D.7 |
| `GET /api/stats` | `200` | D.8 |
| `GET /` | library page (`text/html`) | §8 |
| `GET /play/{id}` | player page (`text/html`) | `404` HTML page for an unknown id |
| `GET /gb_wasm.wasm` | the module (`application/wasm`) | from `--wasm` |
| `GET /static/…` | other front-end files | your layout |

`GET /api/games` query parameters (all optional; invalid values → `400
bad_request`):

* `q` — case-insensitive substring of `title` or `filename`;
* `cgb` — `none` | `dual` | `only`; `mapper` — a mapper name; `playable` —
  `true` | `false`;
* `sort` — `title` (case-insensitive) | `added` | `size`; `order` — `asc` |
  `desc` (default `asc`); without `sort`, the default order (OI-4). Ties
  are broken by `id` ascending, whatever the order.
* `limit` (≥ 1), `offset` (≥ 0) — paging after filtering and sorting;
  `total` counts the filtered games before paging.

### D.4 Uploads

`POST /api/games` accepts either

* `multipart/form-data` with one file part named `rom` (the file name comes
  from the part's `Content-Disposition`), as sent by an HTML form; or
* `application/octet-stream` with the ROM as the body and an optional
  `X-Filename` header (default `upload.gb`).

A file is a Game Boy ROM if and only if all of these hold, otherwise the
response is `400 not_a_rom`:

1. its size is at least 32 KiB and equals `32 KiB << rom[$148]`
   (`rom[$148]` ≤ 8);
2. bytes `$104`–`$133` are the Nintendo logo:
   `CE ED 66 66 CC 0D 00 0B 03 73 00 83 00 0C 00 0D 00 08 11 1F 88 89 00 0E
   DC CC 6E E6 DD DD D9 99 BB BB 67 63 6E 0E EC CC DD DC 99 9F BB B9 33 3E`;
3. the header checksum is correct.

The global checksum is reported, not enforced. Size limit, duplicates and
unsupported cartridges: OI-1, OI-2, OI-3 (ask before implementing them).

### D.5 Persistence and concurrency

R-WEB-9 and R-WEB-10. A game is either fully in the library (listed,
downloadable, with metadata) or not at all — a crash or kill mid-upload
MUST NOT leave a half-written game behind.

### D.6 Screenshots

`GET /api/games/{id}/screenshot.png?frames=N&model=M`

* `frames` 1 … 3600, default 300; `model` `dmg` | `cgb` | `auto` (default
  `auto` = `Model::for_rom`). Out-of-range or invalid values → `400`; a game
  that is not `playable` → `422 unsupported_cartridge`; CGB requested for a
  cartridge without the CGB flag → `400`.
* The game runs headless from power-on for N frames with no buttons held.
  The response is a 160×144 PNG (`image/png`) whose pixels are exactly the
  emulator's frame N:
  * DMG: 8-bit greyscale, shade `s` → `255 − 85·s` (0 = white);
  * CGB: 8-bit RGB, each 5-bit channel `c` → `(c << 3) | (c >> 2)`.
  Any valid PNG encoding (filters, compression level) is fine.
* Rendering 300 frames MUST take under 10 s; a render that does not finish
  within 30 s fails with `500 emulation_failed`.
* Responses MAY be cached by (`id`, `frames`, `model`).

### D.7 Battery saves

* `PUT /api/games/{id}/save` with an `application/octet-stream` body of
  exactly `ram_size` bytes stores the save (`204`). A game without
  `battery`, or a body of any other length → `400 bad_request`.
* `GET /api/games/{id}/save` returns the stored bytes, or `404 not_found`
  if there is none. `DELETE` removes it (`204`; `404` if none).
* Saves persist across restarts and are deleted with their game.

### D.8 Statistics

`GET /api/stats` →

```json
{"games": 12, "uploads_accepted": 3, "uploads_rejected": 2,
 "screenshots_rendered": 40, "emulated_frames": 12000, "uptime_sec": 815}
```

Counters are since the process started: `uploads_accepted` counts `201`
responses to uploads, `uploads_rejected` counts uploads answered with a 4xx,
`screenshots_rendered` counts PNGs rendered (cache hits excluded), and
`emulated_frames` counts frames run for those renders.

## Appendix E — Front-end contract

The QA team's end-to-end tests drive Chromium against these selectors and
hooks. Everything else about the pages — layout, styling, extra features —
is yours.

### E.1 Library page (`/`)

* `#game-list` contains exactly one element per game currently in the
  library, in the API's default order, each with `data-game-id="<id>"`.
  Inside it: an element `.game-title` whose text is the game's title; an
  `img.thumb` whose `src` is `/api/games/<id>/screenshot.png` (any query
  string); a link `a.play` to `/play/<id>`; and a `button.delete`.
* `#search` (text input): within 1 s of typing, `#game-list` shows only the
  games matching as the API's `q` does; clearing it shows all games again.
* `#upload-input` (`<input type="file">`) and `#upload-button`: clicking the
  button uploads the selected file with a multipart `POST /api/games`
  (field `rom`). Within 5 s, on success the new game is in `#game-list` and
  `#upload-status` has `data-state="ok"`; on failure `#upload-status` has
  `data-state="error"` and `data-error-code="<API code>"`, and shows a
  human-readable message.
* `button.delete` deletes the game (`DELETE /api/games/<id>`) without a
  confirmation dialog and removes it from `#game-list` within 5 s.
* No `alert`/`confirm`/`prompt` dialogs anywhere.

### E.2 Player page (`/play/<id>`)

* `<canvas id="screen" width="160" height="144">` (CSS scaling is fine,
  smoothing off).
* Loads `/gb_wasm.wasm` and `/api/games/<id>/rom`; model 1 (CGB) when the
  game's `cgb` is not `"none"`, else 0. If the game has a stored save, it is
  written into cartridge RAM before the first frame; on pause and on leaving
  the page the player SHOULD `PUT` the save back.
* Keyboard (on `document`): arrow keys → D-pad, `KeyX` → A, `KeyZ` → B,
  `Enter` → START, `Backspace` → SELECT. Held keys are held buttons.
* `#pause` toggles pause/resume, `#reset` restarts the game from power-on,
  `#fps` shows the measured frame rate, `#status` shows `running` or
  `paused`.
* Canvas pixels: on CGB, exactly `(c << 3) | (c >> 2)` per channel as in
  D.6; on DMG any four distinct colours, one per shade, used consistently.

### E.3 Test hook `window.gbTest`

Present on the player page (it may be installed once the module has loaded;
tests wait for it); drives the same instance the user sees.

| Member | Behaviour |
|---|---|
| `gbTest.ready` | a `Promise` that resolves once the game is loaded and the first frame has been drawn |
| `gbTest.pause()` / `gbTest.resume()` | stop / restart the real-time loop |
| `gbTest.reset()` | restart the game from power-on (frame 0); stays paused if paused |
| `gbTest.step(n)` | while paused: run exactly n frames with the currently held buttons, draw the last one on the canvas, return the total frame count |
| `gbTest.frames()` | total frames run since the game was loaded or reset |
| `gbTest.frameHash()` | the current frame's FNV-1a-64 hash as 16 lower-case hex digits (equals `gb --hash`) |
| `gbTest.model()` | `"dmg"` or `"cgb"` |

Key events apply to the held buttons immediately, also while paused, so a
`keydown` followed by `step(n)` runs those n frames with the button held.
