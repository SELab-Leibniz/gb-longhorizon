# Smoke test of the v2 showcase — iCode and jiuwenswarm, 20 minutes each

**Date:** 2026-10-03.
**Branch / commit:** `showcase-v2` @ `69fdcbe`.
**Setup:** both agents on DeepSeek `deepseek-flash`, running in parallel. Each had a Harbor `smoke` job: 20 minutes of agent time, a forced kill at minute 8, then the full verifier.
**Trials:**
- `jobs/gb-smoke/task__difUifB` (iCode);
- `jobs/gb-smoke-jiuwenswarm/task__PZgLX3Z` (jiuwenswarm).

## Verdict

* **The stack works end to end for both agents.** Image build with `gb-oracle`, egress boundary, product owner, kill and resume, verifier, hidden backlog checks, audit trail: no infrastructure faults.
* **Neither agent committed within 20 minutes,** so both graded at the starting point (**0.056**). The same happened on `full-spec`; in a 48-hour run this is not a concern.
* **Graded as if committed** (same verifier, on the working trees): **iCode 0.43**, **jiuwenswarm 0.36** after 20 minutes. On `full-spec` the same measurement gave 0.00 and 0.11. The inherited code makes the start much faster, not slower.
* **The backlog bugs are too easy to localize.** iCode had fixed 8 of the 13 planted bugs in its working tree after 20 minutes, jiuwenswarm 4. Most fixes came while the agents were working in the same file on a stub. At this rate the backlog is gone within the first hour or two, and the long run is again the accuracy tail, as in the pilot.
* **The technique highlights do show up:**
  - jiuwenswarm asked the product owner about all 8 decision issues in its first minutes, each question naming the conflicting spec rule;
  - jiuwenswarm used `gb-oracle` to debug `dmg-acid2` frame by frame;
  - iCode compacted its context 7 times and split the work across two sub-agents.

## How each agent worked

**iCode** (274 tool calls, 193 model calls, 7 compactions, 2 sub-agents)
* **Started broad.** It read the whole repository, including all 21 issues (153 references in its session), and kept a running map from each issue to its likely code site. That map appears in its pre-compaction notes, for example: "120 … tie order (ties by lower PC)", "110 … likely won't fix (contradicts OI-2 409)".
* **Delegated at 1:56.** One sub-agent got `gb-tools` and its issues (#112, #120). It finished: disassembler, debugger run loop, both bugs. A second sub-agent got `gb-web` and its issues. The PNG and title fixes in `gb-web` are presumably its work (its session log was cut off by the kill, so this can't be confirmed). It was killed by the minute-8 restart before writing the handlers. iCode had not re-dispatched it by minute 20; its notes say "re-read those diffs before committing them".
* **Main thread.** It implemented every core stub and fixed the CPU, interrupt, palette and model-detection bugs on the way. It ran `cargo test` 10 times (4 more in the tooling sub-agent) and never used `gb-oracle`.
* **Compaction.** It compacted about every 2.5 minutes, from 75–87k tokens down to 5–11k. Its notes carry the issue map, the constraints and the open questions across compactions.
* **Clarification.** It planned to ask about #110, #116 and #121 but had not asked by minute 20.

**jiuwenswarm** (102 tool calls, 93 model calls, 1 compaction, no sub-agents)
* **Read sequentially.** It read GEP 1 end to end, then `README`, `DECISIONS`, `TESTING`, then every core source file.
* **Asked first.** It wrote 8 precise questions to the product owner before writing code. Each named the issue and the spec rule in tension, e.g. "Issue 110 … OI-2 says … Which should win?". All 8 decision issues were covered, including #104 and #113, which the spec already rules out.
* **Implemented the core.** It wrote all 22 core stubs in one pass and fixed four planted bugs while editing those files; one edit is annotated "Issue 101: BCPD auto-increment index is 6 bits".
* **Verified against the oracle.** It compared its `dmg-acid2` frames with `gb-oracle` at frames 119–122, wrote a throw-away OAM dump tool, then ran the Mooneye and Mealybug suites itself.

## What this means for the v2 design

1. **The backlog bugs give away their location.** Three reasons:
   - Each is a single wrong token in the one function a symptom points to (`65520`, `0x7F`, `saturating_add`, a reversed sort).
   - Several contradict the doc comment directly above them (`Model::for_rom`, `title_of`).
   - Six of them sit in files that also hold stubs, so the agent opens them anyway.

   Code localization is exercised only lightly. Ways to harden it:
   - bugs whose symptom shows in a different module from the cause (timer → audio, DMA → sprites);
   - bugs that need a specific sequence to reproduce;
   - fixes spread over several sites;
   - no tell-tale comments;
   - none in files that also hold stubs.
2. **The inherited code speeds things up.** With the structure, interfaces and helpers in place, filling the stubs is quicker than building from scratch: 0.36–0.43 at 20 minutes versus 0–0.11 on `full-spec`. A 48-hour run will likely reach the pilot's plateau (≈ 0.75) within an hour or two.
3. **Clarification and verification are visible already.** jiuwenswarm's questions and its oracle-driven debugging are exactly the behaviour the showcase is meant to show; iCode's are not visible yet at 20 minutes.
4. **Memory and compaction will be exercised** by the run length either way. iCode compacted 7 times in 20 minutes. A backlog released in waves would make memory matter more: the product-owner sidecar could add new issues to `ISSUES/` at, say, 4, 12, 24 and 36 hours, as `harder-task` did with change requests.
5. **Restarts cost iCode its in-flight sub-agent.** The minute-8 kill lost the `gb-web` sub-agent's unfinished work, and the main agent didn't relaunch it within the remaining 12 minutes. In a 48-hour run without chaos kills this matters less. It is still a real robustness observation.

**Recommended next step:** harden the backlog (point 1), and possibly add release waves (point 4), before any long run. Then run a 6-hour pilot to see where each agent plateaus.

## Is v2 still too easy for a 48-hour showcase?

**Yes — for the structured part of the task.** Here is what was left after 20 minutes, as if committed, and how long it should take judging by the 6-hour pilot:

| Work item | Total | iCode @ 20 min | jiuwenswarm @ 20 min | Left after 20 min | Likely time to finish |
|---|---|---|---|---|---|
| Stubbed functions | 37 | 25 done | 22 done | WebAssembly (3), library handlers (4), player JS (5); + tooling (3) for jiuwenswarm | ≈ 1 h; the pilot built all of these from scratch in ~1 h with sub-agents |
| Planted bugs | 13 | 8 fixed | 4 fixed | 5–9 one-line fixes with direct symptoms | well under 1 h |
| Product decisions | 8 issues | 0 asked | 8 asked, all answered | implementing 3 small API changes; 5 are "change nothing" | minutes |
| Issue resolutions written | 21 | 0 | 0 | 21 short notes | minutes |
| Emulator accuracy tail | — | acid2 ✓, Blargg 12/18, Mealybug 0/24, CGB acid2 ✗, sound 1/13 | acid2 ✓, Blargg 17/18, Mealybug 0/24, CGB acid2 ✗, sound 1/13 | Mealybug, CGB acid2, sound, OAM bug, PPU timing | open-ended; the pilot plateaued here |

* **Most of the structured work was done in 20 minutes.** That is all of the core, most of the tooling, and 4–8 of the 13 bugs; the reward would have been 0.36–0.43. What remains of the stubs, bugs, decisions and resolutions is worth about 0.35–0.40 of reward. It is the kind of work the pilot finished in 1–2 hours.
* **Expected curve.** Roughly 0.75–0.85 within 2–3 hours, then the same long plateau on the accuracy tail that the pilot showed (0.71 at 2 h, 0.76 at 4.3 h). The tail is worth about 0.15–0.20 and is only partly achievable: SameBoy itself passes 10 of 24 Mealybug tests.
* **So the 48 hours would be about 3 hours of everything the showcase is meant to highlight, then about 45 hours of accuracy grinding.** Memory and compaction keep mattering in the grind. Clarification and code localization stop mattering after the first hours.

**What would fix that** (in order of effect):

1. **Release the backlog in waves.** The product-owner sidecar adds new issues to `ISSUES/` at e.g. 4, 12, 24 and 36 hours, the way `harder-task` released change requests. Each wave would bring:
   - new bugs;
   - new decisions only the product owner can make;
   - new product features that pretraining doesn't cover (e.g. a save-sharing format, play statistics, a playlist API defined only in the product owner's answers).

   Clarification, localization and memory then matter for the whole run, not just the first hours.
2. **Harder bugs.**
   - The symptom shows in a different module from the cause.
   - Some reproduce only under a specific sequence; some need fixes in several places.
   - No contradicting comments, and none in files that hold stubs.
   - Several should resist a quick oracle diff, so the agent has to build its own reproduction.
3. **Fewer, larger stubs?** Not recommended. The model rebuilds Game Boy internals quickly whatever the granularity; the full-spec start from nothing still reached 0.71 in 2 hours.
