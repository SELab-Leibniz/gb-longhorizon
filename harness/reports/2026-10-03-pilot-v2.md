## What went wrong with the run

The pilot was meant to last 6 hours. Both Harbor processes were started as
background tasks of the operator's tool. That tool caps background tasks at
2 hours, and killed both at the 2-hour mark. Killing Harbor stopped the
agents' containers and skipped the verifier.

Everything the trials produced was kept: agent logs, product-owner logs and
snapshots, egress logs, and the repositories and notices on their volumes.
The verifier was then run by hand: the task's `test.sh`, in each trial's own
image, with its repository and notices volumes. That is exactly what Harbor
would have run. Waves 3 and 4 were never filed. Long runs must be started
detached (`nohup … & disown`); `RUNNING.md` now says so.

## Verdict

* **Both agents finished everything they had been given within the first
  hour or two.** At 2 hours:
  - every delivered bug was fixed and every delivered request was handled as
    the product owner decided;
  - every issue had a written resolution;
  - iCode scored **0.826** and jiuwenswarm **0.873**.

  Both are above the 0.764 calibration of "the pilot's code with every bug
  fixed and every decision implemented".
* **Both declared the work complete early**, iCode at 50 min and jiuwenswarm
  at 87 min. Each declaration filed the next wave ahead of schedule.
* **Each wave was absorbed within minutes.** For example, iCode committed
  fixes for #116, #117 and #118 about two minutes after wave 2 reached it.
  Both had even fixed the wave-4 PNG bug before it was reported, while
  writing the screenshot code.
* **Wave delivery worked as designed.** Every filed wave reached the agent:
  after a commit (88 s, 206 s), between invocations (178 s), or by the
  10-minute limit (607 s).
* **Conclusion: v2 is still far too easy for 48 hours.** Harder bugs and
  waves add work, but not enough to fill hours. The remaining headroom is
  the accuracy tail (Mealybug 0/24, PPU timing, some Color games). The 6-hour
  `full-spec` pilot already showed that is where agents stall.

## What this means

The task is a well-known console with an inherited, mostly working codebase.
For these agents that is a few hours of work, whatever it is wrapped in:

* **Pretraining.** The model knows Game Boy internals well. Rebuilding 37
  central functions took well under an hour.
* **Bugs.** Even bugs with distant symptoms are localized quickly. The issue
  names a component, and a component here is a handful of files the agent
  reads in full.
* **Waves.** Waves only add work at the moment they are filed. An agent that
  is ahead simply waits. iCode's second hour was nearly idle.

## Options

1. **Run the showcase for 6–8 hours instead of 48.** Every technique is
   already visible in the first two hours:
   - clarification: every decision issue was asked about;
   - localization: delivered bugs were fixed 1.4–5.4 min after delivery;
   - compaction: 31 compactions (iCode);
   - verification: 85 `gb-oracle` calls (jiuwenswarm);
   - memory: every wave was handled and every issue resolved.

   This is the cheapest option and an honest one.
2. **Keep issues coming for the whole run.** For example 60–100 issues over
   48 h, with the next wave filed whenever the agent goes idle. They would
   include multi-crate features specified only by the product owner, and
   some requests that conflict with each other. This keeps clarification and
   memory busy, but each item is still minutes of work: 48 hours of small
   tasks.
3. **Leave the Game Boy.** A fictional console (new instruction set, video
   chip and cartridge format), defined only in the spec, with our own
   reference emulator and test ROMs. Pretraining no longer does the work, so
   the run gets genuinely long. This is the largest build effort.
4. **Weight the accuracy tail** (Mealybug, sound, timing). Agents stall there
   rather than show the techniques, so this is not recommended for a
   showcase.
